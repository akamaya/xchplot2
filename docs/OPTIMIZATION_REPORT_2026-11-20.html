01全体の成果と5つの段階

同じ方向の改良を段階的に試した。重要なのは、AES単体を高速化しただけではT1がほとんど改善せず、スレッド間の仕事の再配置と無駄な再計算の除去で大きく伸びたこと。

02WindowsでVRAMが足りなかった理由

当初の課題は、RTX 4070 SUPERが12GB搭載なのに、xchplot2のCUDA実装が必要とする大きなGPUバッファを一括確保できなかったこと。WindowsのWDDM環境では、グラフィックカードの公称容量すべてをCUDAが利用できるわけではない。

デバイスの公称VRAM
12,282 MiB

nvidia-smi 表示値。搭載容量の目安。

実行時に利用可能だったVRAM
約11,069 MiB

デスクトップ・ドライバー・その他のプロセス等で一部が占有・予約される。

必要量 / 使用量空き上限 11,069MiB
従来CUDA一括確保の概算約11,745MiB

必要量が空き上限を超過（GPUバッファ構成の概算）。一括確保できず、CUDA側ではストリーミング経路へ移行。

SYCL版：実測ピーク（当時）10,526MiB

SYCLのバッファ共有・再利用によって約10.5GiBで収まり、GPU内で主要な処理を実行可能になった。

何を変えたか

  • CUDA側は大きなd_storage / pair_a / pair_bなどの領域を同時に保持する必要があり、概算約11.47GiBを要求していた。
  • AdaptiveCpp/SYCL経路では、Xs用バッファを別ステージの領域と重ねて再利用するなどして、ピークを縮小した。
  • 結果として、CUDA一括確保に対しておよそ1GiB規模の節約を実現。具体的な節約量は構成・バッファ予算の比較方法に依存する。

注：ここでいう「メモリ不足」は主にGPUのVRAMであり、PC側の128GB RAMが不足していたという意味ではない。CUDAのストリーミング経路が使えるため、Plot生成自体が不可能だったわけでもない。

03既存の高速なAES方式を見つけた

PoS2で使うAES系ハッシュは、同じ形式のAESラウンドを繰り返す。GPUにはCPUのAES-NIと同じ専用命令がないため、xchplot2ではAES T-table方式で実装していた。ここで、既存研究のTezcan方式に基づくGPU AES最適化を導入した。

従来のAES（4 T-table）

4種類のテーブル（各256×4B＝1KiB）をshared memoryに配置し、各ラウンドで参照。

4KiB / thread block
Tezcan系（T0のみを複製）

T1～T3をT0からのバイト回転で求める。T0の複製とスレッド別の配置により、shared-memoryのバンク競合を緩和。

16x構成：16KiB / block

NVCC/CUDA版では__byte_perm()、SYCL版では32bitのビット回転で実装。計算結果は一致した。

AES単体での結果（512ラウンド）

RTX 4070 SUPER / 4,194,304 states。CUDAとSYCLは異なる時点・ビルド条件での測定。組み合わせて絶対速度の優劣を断定せず、それぞれの従来比で評価。

04ところがT1に組み込んでも、ほとんど速くならなかった

AES単体では最大1.56倍の差が出たのに、T1のmatch処理に組み込むと、17.005秒 → 16.535秒と約2.8%の短縮にとどまった。

warpは通常32スレッド単位で命令を実行する。候補が0件のスレッドと複数件のスレッドが混在すると、多くのレーンがAES計算中に非アクティブになる（warp divergence）。Tezcanでバンク競合を抑える効果も、実処理では見えにくくなると推測した。

05合成ベンチマークで原因を切り分けた

候補数を変えたSYCLベンチマークを作成し、固定（FIXED）／平均1件のランダム（RANDOM）／warp単位で同じ候補数をまとめたGROUPEDを比較。すべて512ラウンド、Pairing AESの計算結果は一致。

短いほど高速。RANDOMだけTezcanの高速化がほぼ消失した（1.057倍）。

ここで方針を転換：AESのラウンドをさらに高速化するより、Pairing AESに投入する候補を詰め直し、全レーンが同じ仕事をしやすくする方が有望と判断した。

28.39%はプログラム内の候補分布モデルから算出された値であり、GPU性能カウンターによる実測稼働率ではない。合成テストはT1本体の検索・書込コストも再現していない。

06T1にLocal Compactionを実装

src/gpu/T1OffsetsSycl.cppに、実験的な局所候補集約（Local Compaction）を追加。単一GPUカーネル内で、256スレッドのグループが候補を共有メモリに集め、Pairing AESの仕事を再分配する。

候補512件×8B＝約4KiB（2本のu32配列）＋カウンター。既存のAES用16KiBと合計約20KiB/ブロック。

安全なフォールバック

1ブロック内の候補が512件を超えた場合、従来の検索済み候補に対するループへ戻して処理する設計。候補を切り捨てない。

この「共有メモリ」はPCのメインRAMでもGPUボード上のVRAMでもなく、GPU内部のSMごとの高速SRAM。したがって候補集約のために追加のグローバルVRAMバッファは不要。

1 Plotのsteady-stateでは66.71秒 → 58.32秒（12.6%短縮）。T1単体は2.07倍の高速化となった。

07T2・T3の既存「二段階処理」が逆効果になっていた

T2/T3にはもともと二段階処理があり、デフォルトでONだった。最初のカーネルで候補ペアをグローバルVRAMに保存し、次のカーネルでPairing AESを一括実行する。ただし、VRAM予算と候補数の上限がある。

既存の二段階処理

カーネルA → VRAMの候補バッファ → カーネルB。バケットをまたいだ大きな集約が可能だが、候補数に応じた追加VRAMが必要。

T1で実装した局所集約

同じカーネル・スレッドブロックの共有メモリ内で候補を詰める。規模は限定されるが、追加の候補用VRAMが不要。

落とし穴：Strength 6で大量のOVERFLOW

実装の容量式はcand_cap = (out_capacity / num_buckets_in_range) × 6 + 4096。候補の採用率はStrengthによって変わり、Strength 6では採用までの候補数が平均で多くなる。既存の「6倍」固定の候補容量では不足しやすかった。

デバッグログでOVERFLOWが多数発生していることを確認。候補バッファの上限を超えると、二段階処理で行った仕事を破棄・巻き戻しして従来の単一カーネル処理にフォールバックする設計になっていた。

今回のモデルでは二段階処理用に49MiBのVRAM予算が宣言されていた。十分な候補を保持できず、二段階処理が高速化ではなく再計算のコストを増やしていた。

10残っている課題・次の実験

  1. 最終コードの正当性検証：T1局所集約ONでCPU/GPUのPairing一致、各Strengthでの動作、生成Plotの検証を完了させる。
  2. T2/T3への局所集約：T1の仕組みを単純コピーするのではなく、既存のペア構造・バッファ容量・Feistel処理を確認して段階的に実装する。
  3. Tezcan AESのT2/T3適用：二段階処理OFF時の単一カーネルに適用し、処理時間・レジスタ・共有メモリ消費を比較する。
  4. 二段階処理の改善：Strength依存の候補容量、早期OVERFLOW検出、再計算コスト、VRAM予算を見直す。Strength 2などでは既存方式が有利な可能性もある。
  5. 比較条件の統一：同じGPU・ドライバー・Plot条件・ウォームアップ・温度・稼働中の別プロセスを揃えて、複数回の中央値/ばらつきを残す。

今回の最も重要な発見は、最適化対象のAESだけ速くしても、GPU全体の実行パターンが悪いと効果が出ないこと。そして、高速化のはずの既存機能も、条件が合わなければ逆効果になることだった。
